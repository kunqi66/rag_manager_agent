## 主线 A：异步任务 —— Redis + Celery（从零学）

### A.1 为什么要学它（先说动机）

看一个场景：用户拖 10 个 PDF 进来导入。每个 PDF 要过 MinerU 解析 + 切片 + 向量化，**一个就要几十秒**。

如果这个逻辑写在 HTTP 接口里，用户点了「上传」就要盯着浏览器转圈 10 分钟，期间服务器线程被占死，别人也没法用。

正确做法：**接口只负责「接单」，立刻返回一个任务 ID；真正耗时的事丢给后台慢慢干**。这就是异步任务的本质。

### A.2 两个主角

**Redis** —— 一个内存数据库，比 MySQL 快几个数量级。在本项目里它同时扮演三个角色（`settings.py` 里用不同的 db 编号区分）：

| 角色 | 用途 | db 编号 |
|---|---|---|
| 缓存 | 会话上下文、FAQ 毫秒级直出 | 0 |
| 任务队列（broker） | Celery 的任务中转站 | 1 |
| 结果存储 | 任务执行结果 | 2 |

**Celery** —— Python 界的标准异步任务框架。核心模型只有 5 个词：

```
producer（谁派活）→ broker（活放哪，就是 Redis）→ worker（谁干活）→ task（一件具体的活）
                                                        ↘ beat（按时间表自动派活）
```

### A.3 本项目的落点（已有代码，可对照看）

| 文件 | 任务 | 触发方式 |
|---|---|---|
| `backend/tasks/import_tasks.py` | `parse_and_index`（解析一个文档入库） | 上传接口派活 |
| `backend/tasks/mining_tasks.py` | `mine_faq_clusters`（聚类挖掘） | beat 每天 02:00 |
| `backend/tasks/stats_tasks.py` | `aggregate_hourly`（看板预聚合） | beat 每 10 分钟 |

**关键概念对照**（学的时候往这几个词上套）：

- **task** = 一个带 `@celery_app.task` 装饰器的函数，你已经在骨架里见过。
- **broker** = Redis，任务排队的地方。看 `celery_app.py` 里的 `broker=settings.celery_broker_url`。
- **beat** = 定时器，看 `celery_app.py` 里的 `beat_schedule`（`crontab(hour=2, minute=0)` = 每天 2 点）。
- **重试** = 任务失败后自动再来。看 `import_tasks.py` 里的 `max_retries=3`。
  ⚠️ `retry_backoff` 对手动的 `self.retry()` **不生效**，详见下方 📘 教学实录里的 bug 记录。
- **软超时** = 防任务卡死，看 `celery_app.py` 里的 `task_soft_time_limit`。

### A.4 学习路径（建议顺序）

1. 先搞懂 **Redis 是什么**：内存存储、key-value、为什么快、TTL（过期时间）。做个小实验：`redis-cli` 里 `SET k v`、`EXPIRE k 10`。
2. 再懂 **队列模型**：为什么「接单快、干活慢」要分开。画一遍 producer→broker→worker。
3. 然后 **Celery 最小例子**：一个 `add(x, y)` 任务，派活、开 worker、看结果跑通。
4. 最后回到本项目：读懂 `celery_app.py` + 三个任务文件，理解 `beat_schedule` 是怎么让「每天 2 点聚类」自动发生的。

### A.5 检验点（怎么算学会了）

- 能说清：用户上传 10 个 PDF 后，从「点上传」到「全部入库」这条路上，Celery 和 Redis 各自干了什么。
- 能自己写一个「每天凌晨 3 点清理过期会话」的 beat 任务。
- 能解释 `retry_backoff` 和 `task_soft_time_limit` 分别防什么。

> ### 阶段二 · 边看边讲（读本项目真实代码）
>
> 读的是 `backend/tasks/celery_app.py` 与 `import_tasks.py`：
>
> - **broker vs backend**：broker 是「待办队列」，backend 是「已完成结果」。两者都指向 Redis，但 db 号不同，不能混用。
> - **`include` 列表**：worker 启动时按它导入任务模块完成注册。漏写 → 派活时 worker 回 `Received unregistered task`，**任务静默消失**。
> - **`conf.update` 里几个参数为什么这么设**：
>   - `task_acks_late=True`：任务执行完才 ack。worker 中途崩溃时任务会重新入队，不丢。
>   - `worker_prefetch_multiplier=1`：一次只预取 1 个，避免长耗时的解析任务在多个 worker 间分配不均。
>   - `task_time_limit=1800` / `task_soft_time_limit=1500`：硬超时直接杀进程；软超时先抛 `SoftTimeLimitExceeded` **进到任务函数内部**，留出清理窗口。**必须软 < 硬**，中间那 300 秒就是清理窗口。
> - **`beat_schedule`**：`crontab(hour=2, minute=0)` = 每天 02:00 自动派 `mining.mine_faq_clusters`。
>
> **用户专门追问 `bind=True`**，展开成五层：
> ① 不加 `bind`，函数收不到 `self`；② `self` 是任务实例，能拿到 `self.request`（含 `retries`、`id`）；
> ③ `self.retry()` 内部抛出特殊的 `Retry` 异常；④ 所以必须 `raise` 出去——只调用不抛，任务会被当成正常返回，重试不会发生；
> ⑤ `max_retries` 用尽后抛 `MaxRetriesExceededError`。

> ### 🐛 现场挖出的真 bug：`retry_backoff` 是个装饰品
>
> **现象**：`flaky` 首次运行超时（120s），worker 日志却写 `Retry in 180s` —— 而代码里明明写的是 `retry_backoff=2`。
>
> **排查**：`grep -rn "retry_backoff" .venv/Lib/site-packages/celery/` → 只在 `celery/app/autoretry.py` 里被读取。
>
> **真相**：
> - `retry_backoff` / `retry_backoff_max` 只服务于 `autoretry_for=` 那种**声明式**重试；
> - 手动调 `self.retry()` 时，这两个参数**完全不读**；
> - 不给 `countdown` 就退回 `default_retry_delay`，定义在 `celery/app/task.py:222` = `3 * 60` = **180 秒**（取值处 `task.py:755-756`）。
>
> **对本项目的影响**：`import_tasks.py` 原有的 `retry_backoff=60, retry_backoff_max=900` 同样是装饰品。
> P1 实现 MinerU 重试时若直接 `raise self.retry(exc=e)`，会平白等 180 秒，而不是设计的 60 秒起步退避。
> 这类「配置了但不生效」的 bug 最难查——日志里什么都不报。
>
> **修复**（已落地）：
> - 沙箱改为显式 `countdown = 2 ** self.request.retries`，重跑 3.8s 通过；
> - `import_tasks.py` 拆掉失效参数，注释写明正确写法 `countdown = min(900, 60 * 2 ** self.request.retries)`；
> - 坑记入 `CLAUDE.md` 的「已知坑 → Celery」。

## 主线 B：混合检索 + 权限下推（RAG 进阶，本项目核心）

你已经做过 RAG，所以跳过 embedding 是什么，直接讲「你的 RAG 在这里要升级的两个点」。

### B.1 回顾：你会的稠密检索

```
问题 "差旅费怎么报" → BGE 转成向量 → 在 Milvus 里找余弦最相似的 N 个切片
```

这条路叫**稠密检索（dense retrieval）**，靠「语义相似」。它有个盲区：遇到**专有名词 / 编号 / 精确关键词**（比如「制度编号 F-2024-031」）时，语义向量抓瞎——因为模型没见过这个编号。

### B.2 新增点一：BM25 稀疏检索

**BM25** 是经典的关键词检索算法，核心思想两句话：

1. **词频（TF）**：一个词在这篇文档里出现越多，这篇越相关。
2. **逆文档频率（IDF）**：一个词越罕见（很少文档里有），它越能区分「这篇相关、那篇不相关」。

「差旅」这种常见词 IDF 低、权重小；「F-2024-031」这种罕见词 IDF 高、权重极大。所以 BM25 擅长精确关键词，正好补稠密检索的盲区。

**关键：Milvus 2.5 把 BM25 做成了内置功能**，你不需要自己实现。只需要在 collection 的 `content` 字段上：

```python
# 让 Milvus 对中文正文自动分词（服务端内置 jieba），并把文本映射成稀疏向量
FieldSchema(name="content", dtype=VARCHAR,
            enable_analyzer=True, analyzer_params={"type": "chinese"})
Function(name="text_bm25", function_type=FunctionType.BM25, ...)
```

### B.3 新增点二：RRF 融合（为什么两个一起用更好）

稠密检索擅长「语义相近但用词不同」（问「怎么退钱」能命中「退款流程」）；BM25 擅长「精确关键词」。真实查询两者都要。

问题来了：两个列表各自给的是**不同量纲的分数**（一个是余弦相似度，一个是 BM25 分），不能直接相加。**RRF（Reciprocal Rank Fusion，倒数排名融合）**就是解决这个的：

```
RRF_score(文档) = Σ 1 / (k + rank_i)
```

大意：不看具体分数，只看**排名**——一个文档在稠密榜排第 1、在稀疏榜排第 3，它的融合分就是 `1/(60+1) + 1/(60+3)`。`k=60` 是固定常数。然后把两榜按融合分重新排，取 Top-K。

**一句话记**：稠密 + 稀疏各自召回一份候选，RRF 按「排名」而非「分数」合并，兼顾语义和关键词。

### B.4 新增点三：权限下推到索引（本项目的灵魂）

这是普通 RAG 和本项目的本质区别。普通 RAG：先召回 Top-K，再判断哪些有权看——但 Top-5 过滤完可能只剩 0-1 条，回答就废了。

**正确做法：把「谁能看」写进检索条件，让 Milvus 在扫描时就只返回有权看的。**

每个切片上冗余存了 ACL 字段（`acl_global` / `acl_departments` / `acl_roles` / `acl_users`），检索时拼一个过滤表达式：

```python
expr = ("acl_global == true"
        " or array_contains_any(acl_departments, ['财务部','成本组'])"
        " or array_contains_any(acl_roles, ['管理层'])"
        " or array_contains_any(acl_users, ['u_1001'])")
```

Milvus 支持 `array_contains_any`（数组含任意一个就算命中），这正好实现 PRD 里的「OR 充分条件」。**部门向下继承**也在这里体现：用户「成本组」的有效部门集合是 `['成本组','财务部','集团总部']`，塞进表达式，就自动覆盖了「授权财务部 → 成本组也能看」。

> 安全兜底：Milvus 上的 ACL 是冗余副本，可能和 MySQL 权威数据短暂不同步，所以召回后还要用 MySQL 复核一遍，不一致的剔除 + 告警（PRD §6.2.3）。这是「防越权」的硬保证。

### B.5 学习路径

1. 补一个概念：**BM25 的 TF-IDF 直觉**（不用背公式，懂「罕见词权重高」即可）。
2. 懂 **RRF**：为什么不同量纲的分数要用「排名」融合。
3. 跑通 **Milvus 混合检索**最小例子：一个 collection，dense + sparse 两个字段，`hybrid_search` + `RRFRanker`。
4. 最后看本项目：`expr` 表达式怎么根据登录用户动态拼出来（这就是「权限下推」）。

### B.6 检验点

- 能解释：为什么「先召回再过滤」会抽干召回，而「权限下推」不会。
- 能写出一个含 `acl_departments` 的 `array_contains_any` 过滤表达式。
- 能说清 RRF 的 `k` 是干嘛的、为什么要 `top_k * 3` 预取再融合。

> ### 知识点 4 详解（用户要求深入）
>
> **"下推"是什么**：借 SQL 的「谓词下推」——把 `WHERE` 条件压到存储/索引层执行，而非捞全量再应用层过滤。
> 权限下推 = 把「谁能看」压到 Milvus 索引扫描层。
>
> **为什么先召回再过滤会废**：普通 RAG 的 Top-K 是在「全体切片」上算的，过滤发生在排名之后。
> 例：问「薪酬怎么算」，最相关的前几篇恰恰是高权限的《高管薪酬细则》——召回 Top-5 过滤后剩 0-1 条，回答废掉。
> 这是结构性缺陷，调参救不了。
>
> **为什么前置过滤不会抽干**：Milvus `search(expr=...)` 是过滤式检索——expr 在扫描时当谓词执行，
> 只遍历通过过滤的实体，Top-K 在「有权切片」这个干净集合上算。召回池从源头就是干净的。
>
> | 做法 | Top-K 在哪个集合上算 |
> |---|---|
> | 先召回再过滤 | 全体切片上算 Top-K，再挑有权 → 抽干 |
> | 权限下推 | 有权切片上算 Top-K → 天然有权且相关 |
>
> **数据怎么存**：每个切片实体冗余 4 个标量字段（源自 MySQL 权威 ACL）——
> `acl_global`(bool) / `acl_departments`(array) / `acl_roles`(array) / `acl_users`(array)。
> 冗余 = 检索时自包含、不回 MySQL，代价是可能和权威数据短暂不同步。
>
> **表达式怎么拼**：四维权限是 **OR 充分条件**（任一维命中即有权，都不中才拒绝 = 默认拒绝）：
>
> ```python
> expr = (
>     "acl_global == true"
>     " or array_contains_any(acl_departments, ['成本组','财务部','集团总部'])"
>     " or array_contains_any(acl_roles, ['普通员工'])"
>     " or array_contains_any(acl_users, ['u_2001'])"
> )
> ```
>
> `array_contains_any(字段, 用户集合)` = 「切片允许集合 ∩ 用户集合」非空 → 命中，天然实现交集判断。
>
> **部门向下继承怎么落进来（最巧妙）**：Milvus 表达式没有「祖先」概念，只知道字符串数组。
> 所以把继承**提前算好**塞进用户集合：用户「成本组」的有效部门集合 = 自身 + 全部祖先 =
> `['成本组','财务部','集团总部']`。切片授权「财务部」时，因集合里含「财务部」→ `array_contains_any` 命中。
> 继承是在生成表达式前查部门树算好的，Milvus 只看到一个更长的列表。
> **「把树结构摊平成集合，交给只会集合运算的引擎」是本项目最值得记住的工程技巧之一。**
>
> **为什么还要后置兜底**：Milvus 的 ACL 是冗余副本，会有时差（刚把用户移出部门、文档重索引未完成 →
> 前置过滤漏放行）。所以召回后必须用 MySQL 权威表复核每个 document_id，不一致的剔除 + 告警。
> 前置过滤管效率，后置兜底管正确性（防越权的硬保证）。
>
> **一张图串起来**：
>
> ```
> 用户提问
>   ├─ 从 JWT 拿 user_id（红线：不信任客户端 user_context）
>   ├─ 查部门树 → 有效部门集合 ['成本组','财务部','集团总部']
>   ├─ 拼 expr = acl_global==true or array_contains_any(...) or ...
>   ├─ hybrid_search(expr=expr)          ← 前置过滤（下推到索引）
>   │     ├─ 稠密 BGE + 稀疏 BM25
>   │     └─ RRFRanker(k=60) 融合
>   ├─ 候选 document_id 去 MySQL 权威复核  ← 后置兜底（剔除 + 告警）
>   └─ 有权切片 → DeepSeek → 回答
> ```
>
> （后续：动手跑纯 Python 的 BM25 / RRF / ACL 过滤时，继续补在本小节之后。）

## 主线 C：Vue 3 组合式 API + TypeScript（从 Vue2 迁移）

### C.1 你会 Vue2，差在哪

Vue2 是 **Options API**（`data` / `methods` / `computed` 分块写）。Vue3 主推**组合式 API**，核心变化一句话：**把同一个功能的代码写在一起，而不是按「类型」散落在不同块里。**

一个组件里，Vue2 要在一堆 `data`、`methods`、`computed` 里来回跳；Vue3 用 `<script setup>` 后，一个功能就一段代码。

### C.2 三个必学概念

| 概念 | 是什么 | 类比 Vue2 |
|---|---|---|
| `ref` / `reactive` | 响应式数据 | 相当于 `data()` |
| `computed` | 派生数据（自动缓存） | 同名，几乎一致 |
| `watch` / `watchEffect` | 监听变化 | 同名，几乎一致 |

```vue
<script setup lang="ts">
import { ref, computed } from 'vue'

// ref：一个响应式变量，.value 读写
const count = ref(0)

// computed：自动跟随 count 变化
const doubled = computed(() => count.value * 2)
</script>

<template>
  <button @click="count++">{{ count }} / {{ doubled }}</button>
</template>
```

### C.3 TypeScript 补什么

你从 JS 转 TS，核心就一件事：**给数据加「形状」**。本项目里，后端每个 Pydantic schema 对应前端一个 `interface`：

```ts
// 对应后端 schemas 里的 Document 响应
interface DocumentItem {
  id: string
  title: string
  fileType: string
  status: 'draft' | 'enabled' | 'disabled'
  chunkCount: number
}
```

先掌握：`interface`（定义形状）、`type`（联合类型，如 `'draft' | 'enabled'`）、泛型 `Promise<T>`、`as` 断言。够用即可，不必钻高级类型体操。

### C.4 Pinia 替代 Vuex

状态管理用 **Pinia**（Vue3 官方推荐），比 Vuex 简洁得多。本项目里，`auth`（登录态 + 权限码）和 `chat`（会话列表）各一个 store 就够了。

### C.5 本项目的落点

| 页面 | 你会用到的关键组件 |
|---|---|
| 登录页 | 表单 + axios 封装 |
| 问答工作台 | **SSE 流式消费**（fetch + ReadableStream）、markdown 渲染 |
| 台账列表 | Element Plus `el-table` + `el-pagination` |
| 导入抽屉 | `el-upload` 拖拽 + 进度轮询 |
| 权限配置弹窗 | `el-tree`（部门树）+ 多选 |
| 运营大盘 | ECharts 折线/柱状/环形 |

### C.6 学习路径

1. 用 Vite 起一个空项目，把「计数器」用 `<script setup>` 重写一遍（体会与 Vue2 的差异）。
2. 给计数器加 TS 类型（`ref<number>(0)`），体会「类型」带来的安全感。
3. 学 Pinia 最小例子（一个 `useAuthStore`）。
4. 回到本项目，仿照一个现成页面写 `el-table` 台账列表。

### C.7 检验点

- 能把一个 Vue2 组件（`data/methods`）改写成 `<script setup>` 且 TS 不报错。
- 能说清 `ref` 和 `reactive` 的区别（对象用哪个、基本类型用哪个）。
- 能消费一段 SSE 流并在页面逐字渲染。

## 学习顺序（结合 P1 开发节奏）

不用三条线并行学，那样会累。**跟着 P1 的开发顺序，用到哪块学哪块**：

| 阶段 | 开发任务 | 学什么 |
|---|---|---|
| 第 1 步 | 文档导入引擎（`import_engine`） | **主线 A**（Celery/Redis）——因为解析要异步化 |
| 第 2 步 | 检索问答引擎（`search_engine`） | **主线 B**（混合检索 + 权限下推）——核心 |
| 第 3 步 | 前端页面 | **主线 C**（Vue3 + TS） |

理由：主线 A 和 B 是后端，先打通后端你就能用接口文档（`/docs`）验证；前端最后学，正好后端接口已经定型，类型都明确。
