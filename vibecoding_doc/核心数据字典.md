| 项 | 约定 | 状态 |

| 分页 | `data = {list, total, page, page_size}` | 📄 见 `backend/core/response.py` |

#### 2.4.1 🔴 `question_embedding` 的二进制契约（✅ 2026-10-14 冻结）

三处 `question_embedding`（`qa_log` / `faq` / `knowledge_gap`）**共用同一种编码**：

| 项 | 取值 |
|---|---|
| 元素类型 | `float32` |
| 字节序 | **小端 `"<f4"`**（显式写 dtype 字符串，**不要**依赖平台原生 `np.float32` —— 在 BE 上恰好也是小端，所以本机测不出来） |
| 维度 | 768（`bge-base-zh-v1.5`） |
| 长度 | **恒为 3072 字节**（`768 * 4`），可当断言用 |
| 归一化 | **已 L2 归一化**（读出来直接点积即余弦） |
| 读写 | 写 `arr.astype("<f4").tobytes()`；读 `np.frombuffer(blob, dtype="<f4")` |

> 🔴 **为什么必须在字典里写死这一条**：这是一个**跨模块二进制契约**，而它错了**不会报错**。
> 字节序写反 ⇒ 向量全是乱码数值 ⇒ 余弦相似度是噪声 ⇒ 症状是
> **「FAQ 发布了但从来命中不了」「聚类永远聚不出簇」**，而日志、接口、类型全部正常。
> 排查者会去怀疑阈值和算法，不会想到字节序。
> 同理，长度不是 3072 的行（历史脏数据 / 换过模型）**必须跳过并计数告警**，
> 硬 `reshape` 会让整轮挖掘抛异常、当天候选全废。
>
> ⚠️ 本条由 be-08 spec §3.1（全局待确认 #141）提出，落地在
> `backend/engines/data_mining_engine/similarity.py` 的
> `from_blob()` / `to_blob()` —— **全项目只有这一对函数允许做这个转换**。

### 5.5 审计动作类型（✅ 已定 2026-10-14）

**全集已冻结**，共 **28 个动作**，逐条清单见

本节只定**命名规则**，不复制清单 —— 两份清单会漂移，以 spec §5.4 为唯一来源。

**命名规则（冻结）**

1. **统一加域前缀**：`auth.` / `department.` / `user.` / `role.` / `document.` / `faq.` / `gap.` / `config.` / `import.`。
   > 字典原示例里的裸 `login` / `logout` **作废**（§9 #43 已定）—— 裸名在跨域检索时无法归组。
2. **多级对象继续加点**：`document.permission.update`、`import.task.retry`。
3. 🔴 **`action` 只增不改**：已落库的历史 `action` **永不重命名**，否则老日志再也查不到。
   新增动作**必须同时**追加进 `audit_service.AuditAction` 枚举与 spec §5.4 的清单。
4. **状态切换成对命名**：`user.enable` / `user.disable` 是两个动作，不是 `user.status.update` +
   一个 `detail.new_status`。理由：查「谁把人停用了」时，`action` 是最常用的筛选条件，
   成对命名让这条查询不必再筛 `detail` 的 JSON。
   ⚠️ 例外的写法已存在：`document.status.update` 用单动作 + `detail.new_status` ——
   因为它有 `draft`/`enabled`/`disabled` **三态**，两两成对会变成 6 个动作。
   判据是**状态的基数**：二态成对、三态及以上用单动作 + `detail`。

**系统自动动作**：`user_id` 固定记字符串 `system`（如缺口自动关闭），与真人操作区分。

> 而 `frontend/src/constants/nav.ts` 的侧栏**不按权限过滤菜单**（5 个入口对所有人可见），
> 所以 `staff` 真的会打开这个页面并发起请求 —— **必须在后端拦，不能靠前端隐藏按钮**（红线 7）。
> 两个码已同步加进 `frontend/src/constants/governance.ts` 的 `PERM`。

**角色分配（`sys_role_permission` 种子）**

| 角色 | 授予 | 理由 |
|---|---|---|
| `sys_admin` / `role_01` | ✅ 全部 5 条显式挂行 | 系统管理员 |
| `kb_admin` / `role_02` | ✅ 全部 5 条 | 知识沉淀与运营是知识管理员的日常职责（PRD §3.3） |
| `staff` / `role_03` | ❌ 一条不给 | 候选与 FAQ 台账是跨部门的治理产物，含他人提问原文 |

> ⚠️ **与 `stats:dashboard:view` 的区别**：看板给 `kb_admin` 且**脱敏聚合**；
> `faq:*` 也给它，但其中 `faq:candidate:list` 返回的是**逐条原文**（未脱敏）。
> 这一条已被 `related_docs` 的权限复核部分兜住（见 be-08 spec §5.7），
> 但**提问原文本身无法按部门过滤** —— 因为聚类的前提就是把跨部门的同义提问聚到一起。
> 这是产品层面的取舍：**要么承认知识管理员能看见跨部门提问原文，要么这个功能不成立**。
> 取前者，并在 PRD §11.1 的隐私说明里认领。

#### 5.6.5 `gap:*` 族的用法与角色分配（✅ 2026-10-14 冻结，销 §9 #68）
