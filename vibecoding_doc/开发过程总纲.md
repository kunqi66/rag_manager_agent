# 开发过程总纲

> 定位：本项目开发的全流程规范，是「spec 驱动开发」的元流程。
> 配套：`.claude/skills/dev-spec/SKILL.md`（执行器）、`spec-templates/`（模板）、`specs/`（产物）。
> 事实来源：`PRD.md`（做什么）、`CLAUDE.md`（怎么写）。本总纲只讲「按什么顺序、过什么门禁」。

---

## 0. 核心原则

**先 spec 后代码。** 任何功能（前端页面 / 后端模块）都必须先产出一份 spec，
评审通过后才允许写代码。spec 是「代码的合同」：代码只做 spec 里写的事；
spec 里没有的，要么回改 spec，要么不做。

## 1. 元流程（四阶段）

```
需求（PRD） → spec → 代码 → 验证
```

| 阶段 | 输入 | 动作 | 输出 | 门禁（不满足不放行） |
|---|---|---|---|---|
| 1 需求 | PRD 对应章节 + 验收标准 | 定位功能对应的 § 与验收编号 | 需求定位 | 找到明确验收标准（A1–A9） |
| 2 spec | 需求定位 + 模板 | 填写 spec 模板 | `specs/` 下的 spec 文件 | 模板字段全填，硬约束已落 |
| 3 代码 | 已评审的 spec | 照 spec 实现 | 代码 + 迁移 + 测试 | 分层铁律 / 安全红线逐条满足 |
| 4 验证 | 代码 + spec 验收标准 | 逐条走查验收 | 回填 spec + 关闭 | 全部验收通过 |

## 2. spec 的粒度与命名

**粒度**：一个 spec = 一个前端页面，或一个后端模块（一组强相关的端点 + 逻辑）。
不要一个 spec 装一个期次（太粗），也不要一个 spec 只装一个字段（太细）。

**命名**：`specs/{P1|P2|P3}-{NN}-{fe|be}-{名称}.md`

| 例子 | 含义 |
|---|---|
| `specs/P1-01-be-auth.md` | P1 第 1 个后端模块：认证 |
| `specs/P1-02-fe-login.md` | P1 第 2 个前端页面：登录页 |

`NN` 按开发顺序递增；`fe` / `be` 区分前后端。

## 3. spec 的生命周期

```
草稿 → 评审 → 冻结 → 实现中 → 已实现 ✅
```

- **草稿**：初次生成，可能有「待确认」项。
- **评审**：用户确认或修改，消除「待确认」。
- **冻结**：评审通过进入实现，此后改需求必须回改 spec。
- **实现中**：照 spec 写代码，逐条勾选验收。
- **已实现 ✅**：全部验收通过，头部标注日期。

## 4. 前后端 spec 如何对齐

前端 spec 的「接口映射」字段，必须逐条对应后端 spec 的「API 契约」。
接口路径、请求/响应类型、错误码三者必须一致，以 PRD §8 为准。

## 5. 绑定三期里程碑

| 期次 | 交付 | 对应 spec（示例） |
|---|---|---|
| P1 | 认证组织 + 知识导入 + 检索问答 | `be-auth` `be-org` `be-import` `be-search` `fe-login` `fe-chat` `fe-documents` `fe-system` |
| P2 | 审计 + 看板 | `be-stats` `fe-dashboard` |
| P3 | 挖掘 + 缓存 + 缺口 | `be-mining` `fe-governance` |

> P1 内部顺序参考 CLAUDE.md「下一步」：
> models/Alembic → security/deps → auth/org 路由 → clients → import_engine → search_engine。
> 第 2 步之前先修掉 `user_context` 越权问题（安全红线第 1 条）。

## 6. 与既有文档的关系

- `PRD.md`：spec 的「需求来源」，spec 必须引用 PRD 的 § 编号与验收编号。
- `CLAUDE.md`：spec 的「怎么写」，硬约束来自 CLAUDE.md 的安全红线 + 分层铁律。
- `核心数据字典.md`：spec 的「字段来源」，spec 的「涉及的表」「API 契约字段」一律从它取；
  它没有的字段/表/枚举，先在字典 §9 追加「待确认」，再在 spec 里标注。
- 冲突时：以 PRD 为准（SSOT）；PRD 没写的以 CLAUDE.md 为准；两者都没有的，
  在 spec 里标「待确认」问用户。

## 7. 反模式（禁止）

- ❌ 跳过 spec 直接写代码。
- ❌ spec 里写「参考 PRD」而不引用具体 § 与验收编号。
- ❌ spec 模板字段留空或写「略」。
- ❌ 代码实现超出 spec 范围（新增 spec 没写的端点/字段）而不回改 spec。
- ❌ 前后端接口路径 / 类型不一致。
